# mimamori — 新生児モニタリングシステム 仕様書

## 1. プロジェクト概要

古いAndroidスマートフォンをカメラとして再利用し、Raspberry Pi上で映像の録画・管理を行い、クラウドのマルチモーダルLLMで映像解析を実施する新生児見守りシステム。

### 1.1 目的

- 新生児の安全を映像監視によって補助する
- 既存のデバイス（古いAndroidスマホ）を有効活用し、低コストで構築する
- LLMによる映像解析で、人間が常時監視できない時間帯をカバーする

### 1.2 ユーザー

- 新生児の保護者（親）

## 3. コア機能

### 3.1 映像取得

- **方式**: Iriun Webcamを使用し、AndroidスマホのカメラをRaspberry Piの仮想カメラ（`/dev/video*`）として認識させる
- **接続**: 同一Wi-Fiネットワーク上でAndroid → Raspberry Pi間を接続
- **映像形式**: Iriun Webcamが提供するV4L2デバイスとしてOpenCVから取得

### 3.2 録画

- **処理場所**: Raspberry Pi上でローカル録画
- **技術**: OpenCVまたはFFmpegによるキャプチャ・エンコード
- **保存先**: Raspberry Piのローカルストレージ（SD / USB外部ストレージ）

### 3.3 LLM映像解析

- **処理場所**: クラウド
- **方式**: Raspberry Piから映像データ（フレーム画像またはクリップ）をクラウドAPIに送信し、マルチモーダルLLMが状態を解析
- **応答**: LLMが解析結果（新生児の状態・異常の有無）をRaspberry Piに返却
- **異常検知時**: Raspberry Piがアラート通知を発行

## 4. 未決定事項

以下の項目は設計・実装前に決定が必要。

### 4.1 クラウドLLMプロバイダー

| 候補 | 特徴 |
|---|---|
| Claude (Anthropic) | マルチモーダル対応、安全性重視 |
| GPT-4o (OpenAI) | マルチモーダル対応、広いエコシステム |
| Gemini (Google) | マルチモーダル対応、Googleインフラとの親和性 |

**決定観点**: コスト、映像解析精度、APIレート制限、プライバシーポリシー

### 4.2 解析の頻度・トリガー

| 方式 | メリット | デメリット |
|---|---|---|
| 定期送信（例: N秒ごと） | 実装がシンプル | コスト・帯域が一定発生 |
| 動体検知トリガー | 不要な送信を削減 | 検知ロジックの実装が必要 |
| 常時送信 | 見逃しが少ない | コスト・帯域が最大 |
| ハイブリッド（定期＋動体検知） | バランス型 | 実装がやや複雑 |

### 4.3 解析対象

優先度を含めて検討が必要。

| 対象 | 内容 | 入力種別 |
|---|---|---|
| うつ伏せ検知 | 危険な姿勢の検知 | 映像（画像） |
| 睡眠状態判定 | 寝ている / 起きている | 映像（画像） |
| 泣き声検知 | 泣いているかどうか | 音声 |
| 呼吸モニタリング | 呼吸の有無・異常 | 映像（画像） |
| 体動モニタリング | 動きの有無・パターン | 映像（画像） |

**注意**: 音声（泣き声検知）を含める場合、Androidからの音声入力パイプラインも別途必要。

### 4.4 アラート通知手段

| 手段 | 特徴 |
|---|---|
| LINE通知 | 日本で普及、APIあり |
| Push通知 | 専用アプリが必要 |
| ブザー（ローカル） | ネットワーク不要、即時 |
| メール | 汎用的だが即時性に欠ける |

### 4.5 ビューワー（リアルタイム映像確認）

| 方式 | 特徴 |
|---|---|
| Webアプリ（Raspi上にWebサーバー） | ブラウザから確認可能 |
| 専用モバイルアプリ | UX良いが開発コスト高 |
| RTSP/HLSストリーミング | 汎用プレイヤーで視聴可 |

### 4.6 Raspberry Piのスペック・OS

| 項目 | 候補 |
|---|---|
| 機種 | Raspberry Pi 4 Model B / Raspberry Pi 5 |
| RAM | 4GB以上推奨 |
| OS | Raspberry Pi OS (Lite or Desktop) |
| ストレージ | microSD + USB外付けストレージ（録画用） |

### 4.7 ネットワーク構成

- **前提**: Wi-Fi接続（Android ↔ Raspi は同一LAN）
- **クラウド通信**: Raspi → インターネット（Wi-Fiまたは有線）
- **検討事項**: VPN・セキュリティ、帯域要件

### 4.8 データ保存ポリシー

| 項目 | 検討内容 |
|---|---|
| 録画保持期間 | 何日分保持するか（ストレージ容量に依存） |
| 自動削除 | 古い録画の自動ローテーション |
| クラウドへの保存 | 映像をクラウドに永続化するか |
| プライバシー | 新生児の映像データの取り扱い |

## 5. 開発手法・ルール

### 5.1 Git / GitHub ワークフロー

- **PR ベース開発**: 必ずブランチを切り、PR を作成する。main への直接 push 禁止
- **ブランチ命名**: `feat/<issue番号>-<短い説明>`, `fix/<issue番号>-<短い説明>`, `chore/<説明>`
- **PR 粒度**: 1 PR = 1 つの論理的変更。300行を超えそうなら分割を検討
- **コミットメッセージ**: Conventional Commits 形式 (`feat:`, `fix:`, `chore:`, `docs:`, `test:`, `ci:`)
- **PR レビュー**: OpenAI Codex による自動レビュー。明確な PR description を記載すること

### 5.2 タスク管理

- タスクや TODO は GitHub Issues に作成する
- バグ発見時は即座に GitHub Issue を作成し、適切なラベルを付与
- GitHub Projects Board でタスクを管理

### 5.3 CI/CD

- テスト・リント・デプロイは GitHub Actions で実行
- PR には CI チェックを必須とする

| ツール | 用途 |
|---|---|
| ruff | リント + フォーマット |
| mypy | 型チェック |
| pytest | テスト |

### 5.4 コード品質

- Python 3.12 以上を対象
- 型ヒントを必ず付ける
- docstring を関数・クラスに付ける
- ruff による統一フォーマット（line-length: 88）

## 7. 制約・前提条件

- Android端末とRaspberry Piは同一Wi-Fiネットワーク上に存在する
- Iriun Webcamが安定して動作する環境を前提とする
- クラウドLLM APIへのインターネット接続が必要
- 24時間稼働を想定（電源供給の安定性が必要）
- 本システムは補助的な見守りであり、保護者による直接的な監視を代替するものではない
